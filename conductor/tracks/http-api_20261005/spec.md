# Specification: HTTP API Service

**Track ID:** http-api_20261005
**Type:** Feature
**Created:** 2026-10-05
**Status:** Complete

## Summary

An HTTP API service that exposes the transcription pipeline: clients upload audio, get an
asynchronous job, poll it for the structured transcript, and can score that transcript against a
ground truth. The service ships as a Docker image.

## Context

Audio Transcriber is a modular pipeline with swappable backends (local faster-whisper, hosted
ElevenLabs Scribe). Today it is reachable only through the Typer CLI. Transcripts carry per-segment
language and optional speakers, and an evaluation harness scores them against ground truths the
team writes for its own (mostly English, code-switched Spanish) recordings. Hosted backends spend
a limited credit budget, so re-scoring must never re-transcribe.

## User Story

As a member of the internal team, I want to send audio to a running transcription service over
HTTP and choose the backend per request, so that other tools and services can use the pipeline
without shelling out to the CLI or installing every engine locally.

## Acceptance Criteria

- [x] `POST /transcriptions` accepts an audio upload plus a backend name and options, and returns
      **202 with a job ID** immediately; the job runs the existing pipeline in the background.
- [x] `GET /transcriptions/{id}` returns the job status (`queued`/`running`/`succeeded`/`failed`);
      on success it includes the transcript in the same JSON the CLI writes, on failure a
      structured error.
- [x] `POST /transcriptions/{id}/evaluation` takes a ground-truth file and scores that job's
      transcript against it (WER and the other `Report` metrics), reusing the
      `score_transcripts` path — it never re-transcribes or spends backend credits.
- [x] `GET /backends` lists installed backends and why the others are unavailable.
- [x] Errors map to HTTP statuses with a JSON body: request-time errors (unknown backend → 400,
      bad ground truth → 422, unknown job → 404); in-job failures (decode, missing credentials,
      transcription) are reported on the job resource.
- [x] `GET /health` returns OK; `audio-transcriber serve` starts the server; server dependencies
      install as an optional `api` extra.
- [x] A Dockerfile and `docker-compose.yml` build and run the service, ffmpeg included.
- [x] Tests use a stub backend, never a live paid one; the README documents setup, Docker usage,
      and example requests.

## Dependencies

None beyond current `main`: `pipeline`, `registry`, `errors`, `schema`, and
`evaluation.runner` / `evaluation.reference`.

## Out of Scope

- Authentication, API keys, rate limiting (internal use for now)
- Persistent job storage — jobs live in memory and are lost on restart (**added to backlog**)
- A distributed job queue (Celery, Redis, …); jobs run in-process
- Corpus (TalkBank) evaluation and baseline-vs-candidate `compare` via the API
- Streaming / real-time transcription
- Cloud hosting and TLS
- A web UI

## Technical Notes

- **Framework:** FastAPI + uvicorn, in an `api` optional extra; the core install stays lean.
- **Jobs:** an in-memory job store behind a small interface (so persistent storage can replace it
  later), executed on a background thread pool — backends are blocking. Concurrency defaults to
  **one job at a time**, configurable, so local Whisper does not overcommit CPU/GPU.
- **Uploads:** configurable max upload size; uploads go to a temp dir cleaned up after the job.
- **Docker:** `python:3.12-slim` + ffmpeg; extras chosen by build arg
  (`EXTRAS=api,faster-whisper,elevenlabs` by default); compose passes `ELEVENLABS_API_KEY` from
  `.env` and mounts a volume for the Whisper model cache.

# Specification: GPU Docker Image

**Track ID:** gpu-docker_20261006
**Type:** Feature
**Created:** 2026-10-06
**Status:** Draft

## Summary

A CUDA variant of the Docker image, so that faster-whisper (including `large-v3`) and speaker
diarization run on an NVIDIA GPU inside the container. GPU use is opt-in through compose; the
default stays the CPU image, unchanged.

## Context

The HTTP API track (`http-api_20261005`) shipped a CPU-only image: `python:3.12-slim`, ffmpeg,
extras chosen by the `EXTRAS` build arg, a non-root `app` user, a `model-cache` volume and a
`/health` healthcheck. On CPU, `large-v3` is far slower than on a GPU, and the CPU image does not
include diarization. The team's host has an RTX 3060 (8 GB) under WSL2, with the NVIDIA container
runtime working (`docker run --gpus all`).

## User Story

As a member of the internal team, I want to run the transcription service on the host's NVIDIA
GPU by opting in through compose, so that `large-v3` and diarization run in a fraction of the CPU
time, while the default CPU setup keeps working unchanged.

## Acceptance Criteria

- [ ] A GPU build of the image (same `Dockerfile`, selected by a build target) installs
      `faster-whisper` and `diarization` with the CUDA libraries they need; the default build is
      still the CPU image, unchanged.
- [ ] `docker compose up` runs the CPU service exactly as today; a GPU service, enabled
      explicitly (a compose profile) and carrying the GPU device reservation, runs the GPU image.
- [ ] In the GPU container a faster-whisper job resolves to `cuda` (recorded in the run manifest)
      and transcribes with `large-v3`; a job with `diarization: true` labels speakers on the GPU,
      given `HF_TOKEN`.
- [ ] On a host without a GPU, the GPU service fails clearly or falls back to CPU as the backend's
      existing `device=auto` does — it never hangs.
- [ ] A measured comparison — `large-v3` on GPU vs CPU on the same clip, and the VRAM used — is
      recorded in the docs, and the README "Docker" section explains GPU use.

## Dependencies

Existing code on `main`: the `Dockerfile` and `docker-compose.yml` from `http-api_20261005`, the
faster-whisper backend's `device=auto` resolution (CUDA first, CPU fallback), and the
`diarization` extra.

## Out of Scope

- GPU support for the non-Docker workstation install (already works with the CUDA wheels)
- AMD/ROCm or Apple Silicon GPUs
- Multiple GPUs or scheduling jobs across GPUs; concurrency stays 1 by default
- GPU for the hosted ElevenLabs backend
- Publishing images to a registry; CI builds
- Tuning `compute_type` or batch sizes beyond a sensible default for 8 GB

## Technical Notes

- **One `Dockerfile`, two targets:** a shared base stage, then `gpu` and `cpu`, with `cpu` last so
  a plain `docker build` is unchanged.
- **CUDA from pip wheels, on `python:3.12-slim`** — as on the workstation. torch 2.14 (via
  pyannote) ships CUDA 13; ctranslate2 4.8.2 needs CUDA 12 cuBLAS and cuDNN 9, from
  `nvidia-cublas-cu12` / `nvidia-cudnn-cu12`, found through `LD_LIBRARY_PATH`. If wheels prove
  insufficient in the container, an `nvidia/cuda:12.x-cudnn-runtime` base is the fallback.
- **Compose:** an `api-gpu` service under `profiles: [gpu]` with
  `deploy.resources.reservations.devices` (`driver: nvidia`, `count: 1`, `capabilities: [gpu]`),
  sharing the model cache volume; default port 8001 so both can run.
- **Smoke checks:** the GPU image proves torch and ctranslate2 see CUDA; the CPU image is rebuilt
  and re-smoked to prove it is unchanged.
- The GPU image is expected to be large (~8–10 GB); measure and document it.
- No change to the backend interface, transcript schema or manifest format.

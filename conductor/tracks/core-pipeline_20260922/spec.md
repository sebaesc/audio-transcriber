# Specification: Core Pipeline and Backend Interface

**Track ID:** core-pipeline_20260922
**Type:** Feature
**Created:** 2026-09-22
**Status:** Draft

## Summary

The core transcription pipeline: ingest audio files, run them through a backend selected by
name, and write normalized transcripts and a run manifest to disk. Includes the backend
interface itself and one reference backend.

## Context

Audio Transcriber exists because transcription tooling hard-wires a single engine, so changing
models means rewriting the pipeline. This track establishes the contract that prevents that:
a stable backend interface, a shared transcript schema, and a pipeline with no engine-specific
code. It is the first track in the repo, so it also creates the package layout, `pyproject.toml`,
and the ruff configuration.

Every later track — a second backend, Docker packaging, diarization — builds on the contracts
defined here. Per `workflow.md`, changes to the backend interface, the transcript schema, or the
run manifest format require approval, so getting their shape right is this track's real work.

## User Story

As a member of the internal team, I want to transcribe a directory of audio files with a backend
I select by name, so that I get consistent, structured transcripts I can trace back to the exact
model and config that produced them.

## Acceptance Criteria

- [ ] A documented backend interface exists; a backend is implemented as one module and registered by name
- [ ] `--backend <name>` selects the engine; no pipeline or CLI code branches on the backend name
- [ ] Every backend's output is normalized to a single transcript schema, validated by a shared conformance test suite
- [ ] Each run writes a manifest recording backend name, model version, effective config, and input checksums
- [ ] Per-file failures are collected in `errors.json` without aborting the batch; exit codes distinguish all-succeeded / partial / aborted
- [ ] One reference backend ships with its doc page (usage, dependencies, credentials, hardware, known limits)

## Dependencies

None. This is a greenfield track: it creates the Python package layout, `pyproject.toml`, and
the ruff configuration itself.

External requirements (not track dependencies):

- `ffmpeg` >= 6.0 on the system path, for audio decode and resample
- The reference backend's model dependencies, installed as an optional extra

## Out of Scope

- More than one backend — additional engines are their own tracks
- Docker packaging and the CUDA image variant
- CI/CD pipeline setup
- Speaker diarization, VAD, and other per-engine capabilities beyond plain transcription
- Resumable runs / skipping already-transcribed files — deferred to a later track
- HTTP API, web UI, hosted service
- A database — outputs stay as files on disk
- Model comparison / benchmarking reports

## Technical Notes

- **CLI framework:** Typer. Resolves the Typer-vs-argparse TBD in `tech-stack.md`; gives typed
  flags and a clean `--help` with little code.
- **Reference backend:** `faster-whisper`, installed as an optional extra
  (`pip install -e ".[faster-whisper]"`). Backend dependencies are never required dependencies
  of the core package.
- **Audio I/O:** ffmpeg via subprocess. Presence is checked once at validation time, before the
  run starts, and failure gives an install hint.
- **Transcript schema:** JSON, defined with dataclasses or Pydantic. Segments carry start, end,
  and text; top-level metadata carries the source file and language. Speaker fields exist in the
  schema but are unpopulated in this track.
- **Output layout:** `out/<run-id>/` containing one `<name>.json` per input, plus `manifest.json`
  and `errors.json`.
- **Backend registry:** an explicit name-to-class registry dict. Entry-point discovery can come
  later without changing the interface.
- **Contracts:** the backend interface, transcript schema, and manifest format are the project's
  contracts. Per `workflow.md`, changes to them after this track require approval.
